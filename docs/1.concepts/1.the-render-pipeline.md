# The render pipeline

Everything happens in two halves that meet at exactly one file. Ingest reads the world — GPX, `tours.json`, elevation tiles, an OpenStreetMap extract — and writes `build/tours.compiled.json`. The render path reads that file and nothing else.

## How it works

```text
data/gpx/*.gpx  ─┐
data/tours.json ─┼─►  pnpm ingest  ─►  build/tours.compiled.json  ─►  scene  ─►  pnpm render  ─►  out/*.mp4
data/dem/*.png  ─┤                                                     (Vue)      (Playwright + ffmpeg)
data/geo/*.json ─┘
```

`pnpm fetch:geodata` sits before all of it, deriving the area from the GPX themselves and pulling the elevation tiles and the OSM extract for it. It runs at ingest time only — see [ADR-0003](../99.adr/0003-draw-the-map-instead-of-fetching-tiles.md).

**The scene is an ordinary Vue app, not a video.** Vite serves it; `scripts/render.ts` opens it in Playwright at exactly 1080 × 1920 and steps it frame by frame:

1. call `window.__setFrame(n)`
2. wait for `window.__frameReady`
3. screenshot `#scene`, pipe the JPEG straight into ffmpeg's stdin

The bridge lives in `src/render-bridge.ts`. `holdFrame(reason)` returns a release function; while any hold is outstanding `__frameReady` stays false and the renderer waits. Fonts and image decodes need it.

## Why it's built this way

**One file is the seam, and it is load-bearing.** No component parses GPX, walks the filesystem or fetches anything. Every frame is reproducible from that one JSON, which is what makes a render deterministic rather than dependent on what the network returned that minute. It is also why ingest copies the DEM tiles into `build/dem/`: the scene resolves its data through Vite globs, which take a literal pattern and cannot follow `HIKE_DATA_DIR`.

**Nothing in the scene animates on its own.** No `requestAnimationFrame`, no CSS transitions, no timers. Every animated value is a `computed` derived from the `frame` ref in `src/frame.ts`. The renderer spends roughly 100 ms of wall-clock time producing each frame while advancing the timeline by 1/30 s, so a value moving on wall-clock time tears or stutters in the output — it is not a style preference but a correctness rule.

**Two measured decisions carry the render time.** The camera may only move between tours, never during one, because contours, land cover, routes and labels are `computed` over the view and rasterising them costs seconds — so layers are built once per framed extent and the zoom itself is a CSS transform over the finished result. And capture is JPEG at quality 95 rather than PNG: ~95 ms per frame against ~260 ms, invisible after an H.264 pass. Together they are the difference between a five-minute render and a twenty-minute one. The full reasoning is in [ADR-0002](../99.adr/0002-render-with-playwright-and-ffmpeg-instead-of-a-video-framework.md).

The output spec — resolution, frame rate, length, overscan — lives in `src/video.ts`, and only there.
